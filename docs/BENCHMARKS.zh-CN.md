## 结论摘要

三款引擎在**同一编译器、同一负载、同一计时器**下进行测试。共 100,000 条记录，
键长 16 字节，值长 100 字节：

| 维度 | yq-DB 表现 | 说明 |
|------|-----------|------|
| 点读（命中 / 未命中） | **与 LMDB 相当，领先 SQLite** | 命中约 2.4–2.8 M / 未命中约 7.1–7.6 M ops/s |
| 全量扫描 | **大幅领先** | 约 142–155 M ops/s，是其他引擎的 2.3–12 倍 |
| 更新 / 删除 | **`normal` 模式领先，`nosync` 模式持平** | 约 257–347 k ops/s |
| 顺序插入 | **最慢，但比随机插入快约 9 倍** | 约 293–296 k ops/s |
| 随机插入 | **最弱** | 约 32 k ops/s |
| 重新打开（崩溃恢复） | **最弱** | 秒级，其他引擎为毫秒级 |

一句话概括：yq-DB 是一款**读与扫描优先**的引擎，其写入与重开路径的代价源于当前
实现上的取舍。下文逐项量化并解释原因。

## 测试方法

- **同编译器、同编译选项。** 三款引擎均使用同一个 MinGW `gcc 14.2.0`，
  以 `-O2 -std=c11` 编译，并分别静态链接为独立可执行文件。第三方源码：SQLite
  amalgamation 3.45.1 与 LMDB 0.9.31（均置于 `bench/third_party/`）。
- **同负载。** 使用同一个驱动 `bench/bench_kv.c`，三款引擎的后端实现统一在相同
  接口之后。键值生成、顺序、批处理与阶段序列完全一致。
- **同计时器。** 统一使用 Windows `QueryPerformanceCounter`（单调高精度计数器）
  测量墙钟时间，不使用任何引擎内部的埋点。
- **可比的持久化设置。** 报告两种同步模式：
  - `normal` —— 各引擎默认的持久化分组（SQLite `synchronous=NORMAL`、
    LMDB 默认 `msync`、yq-DB `YQ_SYNC_NORMAL`）。
  - `nosync` —— 放弃持久化以换取最高吞吐（SQLite `synchronous=OFF`、
    LMDB `MDB_NOSYNC`、yq-DB `YQ_SYNC_OFF`）。
- **两种插入顺序。** `rand` 为乱序插入；`seq` 为升序插入。键采用大端编码，
  以保证字节序比较（三款引擎均使用字节序）与数值序一致。

每组配置在空闲机器上运行一次，取该次吞吐。请将其视为**数量级对比**，而非
认证级基准。

## 负载定义

`N = 100,000` 条记录，`KEYLEN = 16` 字节，`VALLEN = 100` 字节。写入按
**每 1,000 次操作一个事务**（`BATCH = 1000`）分组。各阶段按以下顺序执行，
分别计时：

| 阶段 | 操作 |
|------|------|
| `insert` | 写入 `N` 个新键 |
| `read_hit` | 随机顺序点查 `N` 个已存在的键 |
| `read_miss` | 点查 `N` 个不存在的键 |
| `scan` | 用游标完整遍历一次全部记录 |
| `update` | 覆盖写入 `N` 个已存在的键 |
| `delete` | 删除 `N` 个键 |
| `reopen` | 关闭数据库、重新打开，并读取一个键 |

吞吐以每秒操作数（ops/s）表示，越高越好；`reopen` 以**秒**表示，越低越好。

## 结果分析

### 读：持平到领先

- **点读命中（`read_hit`）** 约 2.4–2.8 M ops/s，与 LMDB（约 2.8–2.9 M）在统计上
  难以区分，约为 **SQLite 的 2 倍**（约 1.1–1.3 M）。yq-DB 命中时返回指向 mmap 的
  零拷贝借用指针，因此一次命中几乎只付出页表查找加一次 B+Tree 下降的成本。
- **点读未命中（`read_miss`）** 约 7.1–7.6 M ops/s，与 LMDB（约 7.4–8.0 M）持平，
  约为 **SQLite 的 3 倍**（约 2.5 M）。未命中在叶子节点查找处即终止，无需拷贝值。
- **全量扫描** 是最亮眼的一项：**142–155 M ops/s**，为 LMDB 的 **2.3–4.7 倍**、
  SQLite 的 **11–13 倍**。在槽式叶子页上顺序遍历游标对缓存友好，且无需逐条物化。

### 写：有序数组的代价

- **随机插入** 是最弱的一项（约 32 k ops/s），与 `normal` 模式下的 SQLite 处于同一
  量级，低于 LMDB。这符合预期：yq-DB 的 memtable 是**有序动态数组**，每次乱序插入
  都要移动数组的一段后缀（`memmove`），即**每次插入 O(n) 摊还**。
- **顺序插入** 快约 **9 倍**（约 293–296 k ops/s），因为升序追加落在数组尾部，无需
  搬移。但它仍慢于 SQLite（顺序）与 LMDB（顺序），后二者使用 B 树插入，不存在线性搬移。
- **更新**（约 257–270 k ops/s）与**删除**（约 330–347 k ops/s）在 `normal` 模式下
  明显领先 SQLite 与 LMDB；但 LMDB 在 `nosync` 模式下将差距缩小（约 269–297 k）。
  yq-DB 在两种同步模式间几乎不变，因为写入先缓存在 memtable，并以每事务 1,000 次
  操作进行批处理。

### 重开：恢复回放的开销

- `reopen` 差距最大：yq-DB 为 **2.1–4.8 秒**，而 SQLite 约 **3 毫秒**、LMDB 约
  **1.5 毫秒** —— 相差三个数量级。由于 1.0 尚未启用 B+Tree 页溢写与日志截断，
  打开数据库时会**把整段日志回放进 memtable**；将 100,000 条记录回放进有序数组，
  会再次叠加同一条 O(n) 插入成本。同样地，顺序数据（2.1 秒）比随机数据（4.8 秒）
  重开更快。

### 同步模式的影响

- 对 **yq-DB** 而言，`normal` 与 `nosync` 在各阶段几乎相同 —— 持久化分组已经摊薄了
  fsync，进一步放开同步模式收益甚微。
- 对 **SQLite** 与 **LMDB**，`nosync` 显著提升写吞吐（例如 LMDB 顺序插入从约 1.0 M
  提升到约 2.8 M ops/s），代价是放弃持久化保证。

## 磁盘占用

在 100,000 条记录的插入阶段之后测量（逻辑数据量，即主文件加当前生效的日志/WAL）：

| 引擎 | 顺序 | 大小（MiB） | 说明 |
|------|------|------------:|------|
| yq-DB | 随机 | 32.4 | 主 `.yqdb` + `.log`（日志尚未 checkpoint） |
| yq-DB | 顺序 | 32.4 | 同上 |
| SQLite | 随机 | 13.4 | 数据库 + `-wal` |
| SQLite | 顺序 | 13.5 | 数据库 + `-wal` |
| LMDB | 随机 | 25.3 | 已用页；文件为 256 MiB 预分配稀疏映射 |
| LMDB | 顺序 | 12.7 | 已用页；文件为 256 MiB 预分配稀疏映射 |

yq-DB 此处占用偏大，主要是因为运行结束后日志被保留、未由 checkpoint 截断。
LMDB 报告的文件大小是其稀疏预分配的映射区域（`mdb_env_set_mapsize`），并不代表
实际写入的数据量。

## 数据背后的已知限制

以下说明用于帮助正确解读数据，而非功能缺陷：

1. **memtable 为有序动态数组。** 最坏情况下插入为 O(n)，这正是随机插入与日志回放
   最慢的根因。未来若改用有序结构（跳表 / LSM），该成本即可消除。
2. **重开会回放整段日志。** B+Tree 页溢写与日志截断在 1.0 中已预留但尚未启用，
   因此恢复成本随日志规模增长。
3. **单写者、单线程。** 本负载为单线程，对比结果不反映多读者扩展性；在这方面
   yq-DB 的 MVCC 快照读正是为并发读设计的。

完整清单见 [README → 当前范围与限制](../README.zh-CN.md#当前范围与限制)。

## 复现方式

基准测试自包含于 `bench/` 目录：

```sh
# 构建三款引擎并运行完整矩阵（Windows PowerShell）
powershell -NoProfile -ExecutionPolicy Bypass -File bench/run_bench.ps1 -N 100000
```

脚本会编译核心引擎与两个第三方引擎，然后针对
`{normal, nosync} × {rand, seq}` 的每种组合依次运行
`insert → read_hit → read_miss → scan → update → delete → reopen`，并输出形如
`RESULT,engine,mode,order,phase,count,seconds,ops_per_sec` 的 CSV 行。

单独运行某一引擎/配置：

```sh
gcc -O2 -std=c11 -DENGINE_YQ     -I include bench/bench_kv.c src/*.c -o bench_yq
gcc -O2 -std=c11 -DENGINE_SQLITE -I bench/third_party bench/bench_kv.c bench/third_party/sqlite3.c -o bench_sqlite
gcc -O2 -std=c11 -DENGINE_LMDB   -I bench/third_party bench/bench_kv.c bench/third_party/mdb.c bench/third_party/midl.c -o bench_lmdb

./bench_yq     bench/data/my.yqdb        100000 normal rand
./bench_sqlite bench/data/sqlite.db      100000 normal rand
./bench_lmdb   bench/data/lmdbbench      100000 normal rand
```
