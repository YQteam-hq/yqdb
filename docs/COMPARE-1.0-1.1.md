# yq-DB 1.0.0 → 1.1.0 性能差距实测报告

## 结论

**1.1.0 相对 1.0.0 唯一实质性的性能提升是 reopen（重开库 = WAL 重放 + 恢复）；insert / read / scan / update / delete 全部等于没变（落在噪声带内）。**

| 指标 | 结果 |
|---|---|
| reopen（rand 序） | 1.0 5.11 s → 1.1 3.55 s，**快 ~1.45×**（nosync 1.55×）|
| reopen（seq 序） | 1.0 2.06 s → 1.1 0.22 s，**快 ~9.4×**（nosync 9.4×）|
| insert | 两版一致：rand ~3.5 s、seq ~0.36 s（×0.95–1.00）|
| read_hit / read_miss / scan / update / delete | ×0.90–1.19，**无变化**（方向还随机）|

要点：1.1 没有让「写入」变快——它的写入路径代码（`yq_memtable.c`）与 1.0 **逐字节相同**。1.1 真正优化掉的是「打开一个已有库」时要重放整条 WAL 的那段固定开销。

## 测评方法（完全沿用仓库自带方法）

- 驱动：仓库自带 `bench/bench_kv.c`（`bench/` 目录在 v1.0.0/v1.1.0 两 tag 间 `git diff` 为空，两版同一套方法）
- 工具链：MinGW-w64 gcc **14.2.0**（与仓库文档一致），`-O2 -std=c11`
- 负载：N=100000，KEYLEN=16，VALLEN=100，BATCH=1000；`normal`(fsync) 与 `nosync` 两种 sync_mode；`rand`/`seq` 两种键序
- 1.0.0 / 1.1.0 源码分别取自 `git tag`，用 worktree 导出并各自独立编译成 `bench_yq_10.exe` / `bench_yq_11.exe`
- 版本真实性：探针调用 `yq_version()`，两二进制分别返回 1.0.0 / 1.1.0
- 统计：每配置 **3 次重复**；主指标取 **3 次最优**（best-of-3，机器有背景噪声，取最优最接近真实能力；最优与中位数结论一致）
- 抗污染：**每次运行使用唯一 db 文件路径**（见文末「坑」）
- 顺序偏差：**版本交替执行**（每个 rep 内 1.0/1.1 相邻），避免某一版总跑在机器变热之后

## 差异根因（代码级）

### 1) reopen 为什么快 ~1.5×（rand）/ ~9.4×（seq）

reopen 的耗时 = 重放 WAL 重建 memtable + 恢复阶段判定「哪些事务已提交」。1.1 改了两处：

- **`yq_wal_scan()` 重写为 64 KiB 块缓冲**（`src/yq_wal.c`）：1.0 每条记录要 2 次 `pread`（头 + payload）外加一次 `malloc`，10 万条 PUT + 200 条 begin/commit ≈ **20 万次系统调用**；1.1 一次读入 64 KiB 再在其上解析，整条 14.7 MB 日志只需约 **224 次** `pread`，payload 复用同一块交换缓冲。
- **恢复阶段改用开放寻址哈希集合判提交**（`src/yq_recover.c`）：1.0 的 `ctx_is_committed()` 对每个操作**线性扫描**已提交事务数组，复杂度 **O(操作数 × 事务数)**；1.1 换成哈希集合 → **O(操作数)**，并把 key/val 收进两个 append-only arena，省掉 10 万次逐条 `malloc`。

**为什么 rand 只快 1.5×、seq 快 9.4×？** 重放时 memtable 的插入成本取决于键序：seq 序是尾部追加 O(1)，rand 序每次插入要 O(n) `memmove`。实测分解：

```
reopen 耗时 ≈  memtable 重放代价  +  WAL 扫描/恢复固定开销
             (两版相同, memtable 未改)   (1.1 优化掉的部分)

seq :  1.0 = 0    + 2.06 s   →   1.1 = 0    + 0.22 s    固定开销省掉 ~1.84 s  (9.4×)
rand:  1.0 = ~3.0 + 2.06 s   →   1.1 = ~3.3 + 0.22 s    固定的 ~1.84 s 被 ~3 s 的
                                                          memtable 代价稀释  (1.45×)
```

### 2) insert 为什么没变

`src/yq_memtable.c` 在 v1.0.0 与 v1.1.0 之间 **md5 完全相同**；`yq_put`、提交路径 `pending_apply`、`yq_txn_commit` 也逐行一致。1.1 对 WAL 写只做了一处安全化：把可能栈溢出的 `uint8_t enc_buf[2048]` 改成有界栈/堆缓冲（小记录仍走栈，本负载记录 ~120 B，无额外分配）。**写入成本模型不变 → 实测不变。**

### 3) 顺带修掉的数据安全缺陷（非性能，但重要）

- **`yq_checkpoint()` 曾调用 `yq_wal_truncate(wal,0)` 直接清空日志** —— 而日志是 1.0 里唯一的持久化副本，等价于删数据。1.1 改为 `wal_compact_from_memtable()`：把 memtable 存活内容重写成新日志后原子 rename。
- **`YQ_TXN_READONLY` 宏值为 0**，1.0 用 `flags & YQ_TXN_READONLY` 判断恒为假 → 只读事务从不注册快照（MVCC 保护失效），且只读事务上仍可写。1.1 改为显式判断读写位。
- 只读句柄上仍能开启读写事务并落盘 → 1.1 拒绝（`YQ_ERR_READONLY`）。
- `yq_wal_append_put` 的 2 KB 栈缓冲对更大 value 会溢出 → 1.1 加边界检查 + 堆回退。
- 辅助文件路径 `log_path[512]` 会静默截断超长库名 → 1.1 提到 `YQ_MAX_PATH` 并显式长度校验。

> 注：这些修复不影响本报告的基准数字（本负载记录小、路径短），但属于 1.1 相对 1.0 的实质改进。

## 附：为什么先前出现过一个「insert 快 10 倍」的假数字

第一轮矩阵曾记录 1.1 的 rand insert = 0.389 s（1.0 为 ~4 s，看着像 10× 提升）。复核确认**是污染造成的假象**：
后台运行中 `rm -rf data/*` 被环境的安全删除策略拦截、又被 `2>/dev/null` 掩盖，导致上一轮的库文件残留，下一轮 1.1 打开的是一个**已经填满的旧库**，insert 退化成近似空操作（0.389 s ≈ 它的 seq insert 时间）。
改用唯一 db 路径 + 版本交替重跑后，该现象消失，1.1 rand insert 稳定回到 ~3.5 s。**本报告全部采用加固后的数据。**
